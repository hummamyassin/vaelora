# VAELORA V2.1 — Plan · Track · Analyze

V2.1 extends V2 checkpoint `f2f86236d50996517a506f10d906edb66823299b`.
The deterministic recommendation engine, nine sourced weather reference areas,
11 selected activity places, photography, attribution, Groq grounding and HTTP
security boundaries remain intact. No geographic records or coordinates were added.

## Track and analyze

`src/domain/tracking/activity.ts` is a pure state machine: idle → recording ⇄
paused → finished. The React screen owns one recorder and one high-accuracy
`watchPosition` subscription. GPS requires Start; it is never requested by mounting
Track. Pause stops the watch and active timer. Resume starts a new route segment;
movement during the pause cannot add distance. Finish stops recording and atomically
saves the completed activity while removing its unfinished draft.

The engine uses accepted-point Haversine distance and active time for average
speed/pace. Current speed uses valid GPS speed or measured speed, with smoothing;
stale speed and insufficient distance produce placeholders. Main pace and average
speed require 50 m. The screen publishes snapshots once per second and checkpoints
to IndexedDB every five recording ticks and on explicit pause/interruption.

GPS policy is explicit in `gpsPolicy`: maximum 40 m reported uncertainty, 15 s point
age, 2 s future tolerance, 30 s continuity gap, an accuracy-aware 3–15 m jitter
threshold, and maximum implied walking/running speeds of 7/12 m/s. Duplicate,
out-of-order, invalid, inaccurate and impossible-jump points do not add distance.
Limits of 30,000 points and 24 active hours bound a session. No interpolation,
street snapping or inferred distance is introduced across gaps.

MapLibre displays measured segments and start/current/finish markers. Dragging
disables follow; the follow button restores it. Finished routes fit their bounds.
MapLibre 6's worker and its shared module are copied from the installed dependency
by `scripts/prepare-maplibre.mjs`, served from a same-origin versioned path and
included in the offline shell. All three map components use the shared setup.

The summary includes activity, local date/start time, distance, active duration,
pace, speed and the route. A relevant available area forecast is captured once at
Start, with its timestamp, temperature, wind and activity score. It is explicitly
an area forecast snapshot, not measured weather along the route. Missing weather
does not block tracking or create fictitious historical conditions.

## Local data and privacy

IndexedDB `vaelora-activities`, schema 1, has `activities` and `draft` stores.
Read/write validation checks version, ordered points, ranges and recomputed distance.
History supports reopen and explicit deletion. Unknown/corrupt records produce an
actionable error; they are not silently migrated or deleted. A failed save retains
the in-memory summary with retry and export. Recovery always starts paused and
requires explicit Resume; time while the page was absent is never credited.

Routes stay on the device. There is no route-upload endpoint, cloud synchronization
or raw-GPS AI context. GPX 1.1 generation is local, completed-only, XML-escaped,
timestamped and segmented; exporting requires explicit confirmation that the file
reveals precise location history. Share Activity downloads a locally generated PNG
with metrics and optional score, excluding route, coordinates, area and date.

Ask VAELORA answers supported questions about today's completed local activities
through a deterministic bilingual summary function. Neither route nor activity
summary is sent to Groq for these questions. Existing planning questions continue
through the single grounded server agent.

OSM tile requests expose the viewed map's tile region to the tile provider, as with
the existing map. They do not upload the recorded polyline. Private route data is
never placed in the service worker's public caches.

## Planning and interface

The original Home dashboard remains primary. Home / Map / prominent Track / Ask
navigation keeps the recording screen two steps away: activity choice → Start.
Compare, Outlook and Saved Areas are secondary views; History lives within Track.

`POST /api/planning` accepts only bounded supported-area IDs and known modes and
durations. It reuses body limits, same-origin checks, rate/concurrency limits,
generic errors and no-store responses. Compare supports two or three areas and
both scores, temperature, wind, precipitation, exact best window and optional
distance to the area reference. Outlook requests three real forecast days through
the existing Open-Meteo adapter; its default remains two days for V2 consumers.
Unavailable forecasts stay unavailable.

Map Score View uses discrete markers for the nine supported references, with
Walking/Running switching and selection back to Home. It makes no block-level
heatmap or verified-place claim. Saved Areas stores supported IDs and bounded local
labels in localStorage, never a live GPS trace or exact user position.

English LTR and Modern Standard Arabic RTL share the same components. Logical CSS,
isolated timer/pace numbers, large actions, progressive disclosure and 390×844
layouts preserve the V2 ivory/navy/sand visual direction. Reduced-motion preferences
remain respected; route updates and fit operations do not animate the camera.

## PWA and operating limits

The manifest provides 192/512 px and maskable icons, a standalone display, scope,
start URL and theme colors. Installation uses the browser prompt when supported,
with platform guidance otherwise. Production registers a versioned public shell
cache; development does not register a worker. Normal `npm run dev` and
`npm run build` prepare map assets; the build's post-step generates the cache list.
Generated vendor copies and offline asset lists are ignored by Git.

After a successful online shell load, offline reopening can recover a local draft,
resume browser GPS, finish and reopen history. Weather, AI and remote basemap tiles
still require connectivity and show unavailable states. The worker never caches
API requests/responses, POSTs, exports, GPS data or remote tiles. Updates do not force
activation over an open recording session.

Reliable background GPS while the screen is locked is **not guaranteed** in a
Web/PWA environment. Hidden pages pause recording; long timer gaps also pause
without fabricating missing time or points. Optional, feature-detected Screen Wake
Lock helps keep the foreground screen awake but is not required. A process crash
can lose the last checkpoint interval (about five seconds). Use one recording tab;
there is no cross-tab ownership lock. Browser storage clearing/eviction removes
local history. No native-device GPS accuracy or battery guarantee is claimed.

# V2.3 real user experience

## Dynamic location and deterministic planning

Home follows plan → nearby discovery → featured places → local progress. Quick Start invokes the existing recorder, preserving lifecycle, GPS filters, metrics, persistence and recovery. Detailed forecasts, filters, Compare Areas, 3-Day Outlook and Saved Areas remain accessible.

`serviceCities` in `src/lib/dynamic-location.ts` defines the enabled polygon and cell resolution. **This is VAELORA's urban Amman service area, not an official municipal/cadastral boundary or full GAM jurisdiction coverage.** It includes existing reviewed places/reference areas with a conservative north/east extent excluding Zarqa. Fringe locations can be outside service. Other cities require reviewed configuration and boundary tests; none are enabled.

The browser validates coordinates against the polygon and sends only a 0.02-degree cell ID to `/api/discovery` (roughly 2.2 km north/south, 1.9 km east/west). The server validates cell/polygon intersection and requests its centre's forecast. Edge-cell centres can lie outside the polygon while their coverage overlaps it. Cells are never drawn. This is regional sampling, not street-level weather precision.

Dynamic coordinates never gain terrain, surface, access or safety attributes. Only the existing 11 reviewed records supply place facts. Search results are coordinate references, **not new activity recommendations**. Featured Sports City, King Hussein Park and National Gallery Park retain existing evidence. Opening a profile retrieves conditions on demand; place-fit/window appears only if eligible. No new venue facts or NEW badges were invented.

The unchanged scorer maps environmental severity to 90/65/30. Place-fit scores additionally reflect suitable/limited activity fit. They are labeled separately, not treated as confidence percentages. Missing data yields no score; poor/incomplete windows yield no outing recommendation. No AQI or route safety is inferred. Ground preferences filter reviewed places, and heat/wind constraints use the existing policy.

Daily plans require a complete 30/60/90-minute outing and use the worst covered hour. States: no location, now, later, poor and insufficient. Nearby ordering: usable now/later, authoritative place fit, evidence status, approximate straight-line distance, stable ID. Exact distance/radius filtering runs in the browser. A 1.6 km server candidate margin accounts for cell-centre displacement. Default radius 5 km; alternatives 3/10 km. No travel times are invented.

Weather work is bounded by the reviewed dataset, batches of three, in-flight deduplication and the existing 10-minute/64-entry successful cache. Dynamic requests share cell centres; reviewed places retain their own public coordinates. Visible Home refreshes every minute and stops refreshing while tracking/elsewhere. Errors never substitute stale weather. Legacy weather/AI contracts remain intact.

## Search

`POST /api/search` accepts only a 2–100 character query and en/ar locale. Submitted text goes to Photon, bounded by the service envelope; responses are filtered against the polygon. No autocomplete or reverse-GPS requests. Public Photon accepts default/de/en/fr: Arabic uses default for local names, preserving Arabic query text. Translation/coverage depends on OSM.

Limits: 8-second timeout, 100 KB response, 10 provider features/6 results, 24-hour/200-entry cache, one active outbound request and at least 1.1 seconds between outbound requests per process. HTTP origin, JSON size/time and request budgets apply. Provider HTML is never rendered. Manual reference selection remains available when search is offline/unavailable.

Default: `https://photon.komoot.io/api/`. Optional server-only `VAELORA_GEOCODER_URL` switches to an operator-managed HTTPS Photon service; browsers cannot supply that URL. The demo permits reasonable use but may throttle and has no uptime guarantee. **Before substantial multi-instance public traffic, configure deployment-wide limits and a suitable provider.** This task does not deploy.

Sources checked September 23, 2026: [Photon API](https://github.com/komoot/photon/blob/master/docs/api-v1.md), [demo policy](https://github.com/komoot/photon#demo-server), [availability limitations](https://github.com/komoot/photon/discussions/598). The [GAM spatial profile](https://media.ammancity.gov.jo/EBV4.0/Root_Storage/EN/EB_List_Page/Amman_spatial_profile_UN-Habitat.pdf) describes municipal geography; our service polygon is not a digitization of that map.

## Local recap, sharing and progress

Recap shows the full local route first, real distance/time/pace/speed, date and available start forecast. Missing GPS/weather stays explicit. IndexedDB schema and the tracking engine are unchanged; history opens the same recap.

Map Focus, Performance and Minimal are generated locally as 1080×1440 PNGs in English/Arabic. Canvas uses no map tiles or external assets. Original coordinates, place names, timestamps and activity IDs are absent from the exported image/model. Only normalized drawing points and metrics enter rendering.

Every image removes 300 m zones around both recorded endpoints, including every later visit. Edges intersecting a zone are discarded completely, with a conservative numeric buffer. Pauses/hidden gaps never get bridged. Short routes may disappear entirely. Remaining shapes can still be recognizable: endpoint protection is **not anonymity**. Original records remain unchanged. GPX remains a separate explicit export with the existing precise-location confirmation.

Save Image downloads locally. Native file sharing is used when supported; otherwise it downloads. Cancellation/errors are visible. No route/snapshot goes to Groq, our servers or analytics. As before, OSM tile requests reveal the viewed region to the tile provider. No analytics were added.

Progress uses completed local activities and Monday-based Amman weeks. It shows this week's count/distance/active time, previous *full* week totals only when both periods contain activities, and separate valid walking/running pace. Pace excludes activities without usable distance/points. Longest walk/run this month are factual bests; no misleading fastest-pace comparisons, fake badges or social stats. Empty history and storage failure remain distinct.

## Identity, AI and PWA

Burgundy/red, warm off-white and charcoal replace the dominant lime identity. Lime is reserved for Start/live/GPS-positive states. Generated SVG art supports park/nature/urban/running/walking/featured categories with original restrained diamond/check motifs. `LocationPhoto` is a compatibility facade over `LocationArt`: no UI imports photo metadata or loads location photographs. Historical photo assets and attribution tests remain archived, unused by the application.

The grounded AI agent/provider adapters are unchanged. Ask identifies its reference-area context; dynamic GPS cells and private routes never enter model input. Existing AI evals remain mandatory.

PWA caches public shell/scripts, not API/search responses or routes. Weather/search/AI require network; local history, tracking and recap remain available within the offline shell. **Web/PWA background or locked-screen GPS cannot be guaranteed, particularly on iOS.** Leaving foreground pauses recording. No native/background promises are made.

## V2.3.1 pre-deployment corrections

The application shell now gives each active screen one dock-aware scroll viewport,
including safe-area and keyboard-focus clearance. Daily Plan exposes distinct
recommended, unavailable-weather, no-window and no-location states; recording stays
available without presenting it as a recommendation.

Map selection is rendered separately from clustered markers, so the chosen reviewed
place remains identifiable and can be centered without changing scores. The map also
has a loading state and a marker legend. Unfinished recordings take priority over the
new-activity control and must be resumed or explicitly discarded.

Share exports still remove 300 m around both route endpoints and never embed raw
coordinates, IDs, timestamps or the original route. A route is treated as useful for
visual display only when enough privacy-safe points span both axes. Otherwise the
export uses a clearly labelled metrics-led geometric composition; it does not enlarge,
reconstruct or imply a hidden route. Map Focus, Performance and Minimal use distinct
layouts, and canvas generation remains fully local. GPX remains the separate, explicit
precise-route export.
